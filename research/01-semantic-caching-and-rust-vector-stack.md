# Semantic Caching, Prefix/KV Reuse, and the Rust Vector Stack for Caliban

*Research note, 2026-10-02. Scope: response caching (exact + semantic), prompt/prefix/KV-cache reuse, eviction, multi-tenant isolation and side channels, and the Rust crates for the data plane.*

**Summary.** The 2025–2026 literature says three things. First, **static-threshold semantic caching (GPTCache-style) is not safe to sell as a default.** False hits are common, and the fix is per-entry or per-category thresholds learned online with an explicit error budget (vCache, ICLR 2026; category-aware caching), plus asynchronous LLM-judge verification for borderline matches (Krites). Second, **shared caches are an attack surface, and gateways are where isolation usually breaks.** Timing and `cached_tokens` side channels leak other tenants' prompts across shared KV/prefix caches (NDSS 2025, ICML 2025 audit). Semantic caches can also be poisoned through embedding-key collisions (86% hijack rate). Two 2026 papers (KeyPooling, CacheProbe) show that relays and gateways that pool upstream credentials collapse the providers' per-org cache isolation, and that this happened on OpenRouter and in all five open-source gateways tested. Third, **the biggest cheap win is not a semantic cache.** It is steering provider prompt caching, which gives 90–95% input discounts, through stable prefixes and per-tenant upstream identity, plus exact-match caching with datasource-version-aware invalidation. Semantic caching belongs in the stack, but it should be scoped per tenant, gated by intent category, and verified. KV-cache reuse such as RadixAttention, LMCache, or CacheBlend only matters for the sovereign/on-prem deployments where Caliban runs the inference engine. The Rust ecosystem is ready for all of this: fastembed-rs/ort for in-process embeddings, usearch or hnsw_rs for hot in-memory ANN, Qdrant (tiered multitenancy, quantization) as the durable vector tier, tantivy for BM25, and moka/foyer for the exact-match tiers.

## Risks & failure modes

| Risk | Mechanism | Evidence | Mitigation in Caliban |
|---|---|---|---|
| **False semantic hits** | A static cosine threshold confuses "revenue Q3 2025" with "revenue Q3 2026", or differs only in a parameter. | vCache: static thresholds give unpredictable error ([2502.03771](https://arxiv.org/abs/2502.03771)). GenCache: "negative hits" from ignored parameters ([2511.17565](https://arxiv.org/abs/2511.17565)). | Learned per-entry thresholds with an error budget, slot/entity equality checks (numbers, dates, IDs must match exactly), and category gating. |
| **Density-dependent error** | Dense clusters such as code give false positives; sparse ones such as chat give misses. | [2510.26835](https://arxiv.org/abs/2510.26835) | Per-intent thresholds, TTLs and quotas. |
| **Multi-turn context errors** | A follow-up ("and for EMEA?") matches a standalone entry. | MeanCache context chains ([2403.02694](https://arxiv.org/abs/2403.02694)) | Key includes a hash of the canonicalized prior context. By default, apply semantic cache only to turn 1 or to context-free intents. |
| **Staleness** | The underlying datasource changed, but the cached answer still matches. | GroundedCache: 51.5% unsafe serving under drift without version gates ([2605.27494](https://arxiv.org/abs/2605.27494)). | Datasource epoch vectors stored in each entry and checked at lookup (see design). |
| **Cache poisoning / key collision** | An attacker crafts a prompt that collides with a victim's key and plants a malicious response, including tool-call hijacking. | 86% hijack, 90.6% tool hijack ([2601.23088](https://arxiv.org/abs/2601.23088)). LaCache defense ([2608.01718](https://arxiv.org/abs/2608.01718)). | No cross-tenant semantic sharing. Per-user scope for tool-call outputs. Insert-time perplexity screen. Never semantic-cache tool calls that have side effects. |
| **Cross-tenant timing leakage (self-hosted KV)** | A shared radix/prefix cache gives hit-vs-miss timing, enabling token-by-token prompt reconstruction. | NDSS 2025 ([paper](https://www.ndss-symposium.org/wp-content/uploads/2025-1772-paper.pdf)). KVGov ([2608.09225](https://arxiv.org/abs/2608.09225)). PrefixWall ([2603.10726](https://arxiv.org/abs/2603.10726)). | Per-tenant HMAC salt injected **after** public prefixes (system/tool boilerplate). |
| **Gateway key pooling (upstream providers)** | Caliban forwards many tenants through one OpenAI/Anthropic credential, so the provider's per-org isolation becomes a single org. `cached_tokens` and latency then leak across tenants. | KeyPooling: all 5 OSS gateways leaked ([2608.17485](https://arxiv.org/abs/2608.17485)). CacheProbe on OpenRouter ([2605.30613](https://arxiv.org/abs/2605.30613)). Gu et al. ([2502.07776](https://arxiv.org/abs/2502.07776)). | Per-tenant upstream domains: BYOK, or an Anthropic workspace / OpenAI project per tenant. Otherwise, a tenant-derived namespace that reaches the provider's cache key. See the provider docs below. |
| **Hidden upstream sharing** | Routing to other resellers/gateways silently merges caches. | [2608.20732](https://arxiv.org/abs/2608.20732) | Only route to first-party providers or audited upstreams. Publish the routing graph. |
| **Within-tenant ACL leakage** | User A (finance) caches an answer built from data user B (sales) is not allowed to see. B gets a semantic hit. | Follows from RAG plus shared cache. No paper needed. | The key must include an **ACL/permission-set fingerprint** for any response built from datasource content. |
| **PII persistence** | Raw prompts and responses with PII are stored in the cache, which conflicts with retention and erasure duties. | — | Cache only anonymized forms (post-PII-layer). Rehydrate per request. Support per-tenant purge with crypto-shredding of per-tenant keys. |
| **Compression breaks provider caching** | The token-reduction layer rewrites the prefix on every request. | CAPC ([2607.15516](https://arxiv.org/abs/2607.15516)) | Compress only the stable prefix, deterministically. Never compress the cached prefix per query. |
| **Provider cache economics** | Write premiums (1.25x for 5 min, 2x for 1 h on Anthropic; 1.25x on newer OpenAI models) lose money on prefixes that are never reused. | [Anthropic docs](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching), [OpenAI docs](https://developers.openai.com/api/docs/guides/prompt-caching) | Predict reuse per prefix hash. Set breakpoints only where expected reads exceed break-even. |

## Recommended design for Caliban

### 1. Tiers (evaluated in order, cheapest first)

| Tier | What | Key | Store | Applies when |
|---|---|---|---|---|
| **T0 Provider prefix steering** | Not a Caliban cache. Make upstream prompt caching hit: canonical ordering (tools → system → ontology/context modules → history → user), deterministic serialization, auto-placed `cache_control` breakpoints (Anthropic, max 4), and `prompt_cache_key` = HMAC(tenant) (OpenAI). | Provider-side | Provider | Always. This is the biggest $ lever (0.05–0.1x read price). |
| **T1 Exact-match response cache** | Full response replay. | `BLAKE3(scope ‖ route_family ‖ canonical_request ‖ acl_fp ‖ ds_epochs ‖ pii_mode)` | moka (L1, per pod) → foyer (RAM+SSD) or Valkey (shared within tenant) | `temperature==0` or explicit `cache: true`, no side-effecting tools, response not streamed-only. |
| **T2 Semantic response cache** | Nearest neighbour on the embedding of the **anonymized, canonicalized** last user turn plus a context hash. | ANN within `(tenant, scope, intent, acl_fp)` partition, then verified-threshold decision, then slot-equality check, then epoch check | usearch/hnsw_rs per hot tenant in RAM; Qdrant collection with `is_tenant` payload as the durable tier and for warm restarts | Only for intents on a cacheable allowlist (FAQ, docs QA, definitional, NL→SQL *plan*). Off for personalized, time-sensitive, or tool-executing intents. |
| **T2b Near-hit as hint** | 0.75 < sim < threshold: inject the cached Q/A as a few-shot exemplar instead of serving it. | Same | Same | Analytics/NL-to-code intents ([2601.11687](https://arxiv.org/abs/2601.11687)). |
| **T3 Plan / tool-result cache** | Cache agent **plans** (APC) and **read-only tool results** keyed on `(tool, normalized_args, ds_epoch)`. | Canonical intent plus slots (W5H2-style) for plans, BLAKE3 for tool calls | foyer / Qdrant | Agent nodes. Tools must declare `idempotent: true` and their datasource dependencies. |
| **T4 KV/prefix reuse** | SGLang RadixAttention or vLLM + LMCache (CacheBlend for RAG chunks). | Engine-side, with a per-tenant salt after the public prefix | GPU/CPU/SSD | **Sovereign/on-prem only**, where Caliban runs inference. |

### 2. Scoping and tenant isolation (non-negotiable)
- **Default scope = tenant.** Optional narrower scopes are `tenant/app(node)` and `tenant/user`. **There is no cross-tenant scope**, except a curated, read-only "public" static tier (Krites-style) holding Caliban-authored content only.
- **Upstream identity:** each tenant maps to its own provider domain: BYOK, or an Anthropic workspace / OpenAI project per tenant. Shared pooled keys are allowed only for the free tier, and only with `prompt_cache_key` = HMAC(server_secret, tenant_id), plus a documented caveat. This follows the KeyPooling defense contract.
- **On-prem engines:** salt = HMAC(secret, tenant_id), inserted as a token block after the shared public prefix. This keeps most reuse at about a 2% cost ([KeyPooling](https://arxiv.org/abs/2608.17485)).
- **`acl_fp`** = hash of the sorted set of (datasource, row/column policy) the caller is entitled to. It is required in every key whose response was grounded in tenant data.
- **CI isolation audit:** run the [Gu et al.](https://arxiv.org/abs/2502.07776) hypothesis test (two synthetic tenants, timing plus `cached_tokens`) against every release and every new upstream route. Publish the p-values in the trust report.

### 3. Threshold strategy
1. Start each intent category with a conservative static threshold, calibrated offline per embedding model on Caliban's own labeled pairs. Never ship a single global value.
2. Run **vCache-style per-entry learned thresholds** with a per-tenant error budget δ, defaulting to 1% and configurable from 0.1% to 5%. Learn from (a) shadow re-generation on a 1–2% sample of hits judged by an LLM and (b) explicit user feedback.
3. **Grey zone** (just below threshold): serve fresh, and queue an async judge (Krites). If the judge approves, promote the pair, which lowers that entry's threshold.
4. **Hard guards** that run before any semantic hit is served: extracted entities and slots (numbers, dates, IDs, product/region names via the intent classifier's slot filler) must be equal, and the response language must match.
5. Rescore candidates at full precision (f32/f16) before the threshold decision. Quantized distances (b1/PQ) are used only for candidate generation.

### 4. Invalidation tied to datasources
- Every connector in the ontology layer maintains a **monotonic epoch** per `(tenant, datasource, object)`. The epoch is bumped by CDC, webhooks, or a periodic content-hash poll.
- Every cache entry stores its **dependency set** `{(ds, object, epoch)}`, captured from retrieval provenance and tool calls during generation.
- **Lookup-time validation:** if any current epoch is greater than the stored one, treat it as a miss (lazy, O(deps)). A background sweeper deletes stale entries.
- Category TTLs act as a backstop (e.g. docs-QA 7d, metrics-QA 1h, NL→SQL plan 30d, since plans depend on schema rather than data). Schema changes bump a separate `schema_epoch` that invalidates plans.
- For RAG answers, add the GroundedCache gates: re-retrieve the top-k IDs (cheap), and require ≥ X% overlap with the cached evidence IDs.

### 5. PII interplay
- Cache keys and stored values use the **post-anonymization** text, with placeholders. On a hit, re-hydrate with the *current request's* mapping. A placeholder that is absent in the current mapping forces a miss.
- Per-tenant envelope encryption of cached values makes "delete tenant" a key-shred.

### 6. Crate choices (data plane)
- Embeddings: **fastembed-rs on ort** (CPU, small BGE/E5-class model, ~384–768 dims) in a dedicated thread pool. **TEI** sidecar for GPU or larger models. **candle** for the intent/slot model.
- Hot ANN: **usearch** (f16 storage, i8 optional), one index per hot tenant partition, LRU-evicted by tenant. Fall back to **hnsw_rs** if the C++ FFI is unacceptable.
- Durable vectors and RAG: **Qdrant** server (tiered multitenancy, `is_tenant`, binary/TurboQuant with rescore). **Qdrant Edge** or **LanceDB** for single-node sovereign deployments. Postgres (pgvector/pgvectorscale) as a pluggable adapter only.
- Lexical/hybrid: **tantivy** (BM25), fused with RRF.
- KV stores: **moka** (L1), **foyer** (L2 hybrid), Valkey for cross-pod sharing within a tenant.
- Hashing: BLAKE3 for keys, HMAC-SHA256 for tenant salts.

### 7. Metrics (per tenant × intent × tier)
- Hit rate, **verified false-hit rate** (from shadow sampling) versus budget δ, error-budget burn.
- Tokens and $ saved, split into provider-cache reads (`cache_read_input_tokens` / `cached_tokens`) and Caliban-cache hits. Track cache-write $ that was never read back (wasted premium).
- Added latency of the lookup path (embed + ANN + checks) at p50/p99. Target < 5 ms for T1 and < 15 ms for T2 on CPU.
- Staleness: hits invalidated by epoch, and stale-served incidents (should be 0).
- Grey-zone judge approval rate, and threshold drift per entry.
- Eviction churn, bytes per tenant, ANN recall@k against brute force (nightly sample).
- Isolation audit p-values per route (CI), and anomaly alerts on cross-user near-duplicate inserts (poisoning signal).

## Open questions
1. **Embedding model choice** for cache keys versus RAG. Should they be one model or two? A small fast model works for cache keys, but multilingual tenants need a better one. A per-tenant model change requires a re-embed and threshold re-calibration.
2. **Error-budget semantics for customers.** Is δ a contractual SLA? Who adjudicates a "wrong" cached answer (LLM judge or human)?
3. **Placeholder-templated caching** after PII anonymization raises hit rates. Does re-hydration create subtle correctness bugs, such as gendered grammar or numeric PII that matters to the answer?
4. **Within-tenant cross-user sharing:** is `acl_fp` scoping sufficient, or do regulated customers require per-user scope (which kills hit rate)? We should measure the hit-rate cost on real traffic.
5. **Provider-domain-per-tenant operations:** can Caliban automate Anthropic workspace / OpenAI project creation at scale, and what does it do on Bedrock/Vertex, where Anthropic caching is org-level?
6. **Streaming replay:** should cached hits be re-streamed with synthetic pacing? Instant replay is itself a timing signal within a tenant.
7. **GenCache/APC for nodes:** is the plan-template abstraction stable enough across Caliban's agent DSL to justify building it in v1, or should it wait until v2?
8. **On-prem KV sharing across business units** of one customer: should the default be full isolation (KVGov salt), or PrefixWall-style selective sharing?
